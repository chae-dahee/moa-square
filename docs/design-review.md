# moa-square 적합성 검토와 권장안

## 종합 판단

Calendar Core + 단일 서버 + REST/CalDAV Adapter 구조는 앱과 외부 캘린더가 같은 공유 일정을 사용하는 moa-square의 방향에 적합합니다. MCP를 후순위 선택 기능으로 분리하면 초기 범위도 제한할 수 있습니다.

이 구조는 닿님의 지시에 따라 초기 Supabase 직접 접근 제안을 대체합니다. 서버 프레임워크는 Fastify, DB·인증은 PostgreSQL과 Supabase(내부 인프라)로 확정하고, 알림은 상시 서버 내장 스케줄러와 Expo Push로 발송하며, CalDAV 최초 공개는 읽기 전용으로 확정합니다. 반복·예외 세부 지원 범위와 소유자 탈퇴 방식 등 일부 정책은 미결정입니다.

권한과 일정 규칙을 Core에 모으면 프로토콜별 동작 차이를 줄일 수 있습니다. 다만 CalDAV 호환성·인증과 예약 작업 운영이 개발 책임에 추가됩니다. 단일 서버로 배포 단위를 줄여도 프로토콜 구현 자체의 복잡성이 사라지지는 않습니다.

## 기존 검토의 갱신

반복 일정·시간대·알림·초대·접근성에 대한 기존 검토는 계속 유효하며 해결 위치를 Core와 단일 서버로 옮깁니다.

| 초기 설명 | 현재 설계 |
| --- | --- |
| 앱이 Supabase DB·Realtime에 직접 접근합니다. | REST Adapter를 통해 Core를 호출합니다. |
| Supabase를 필수 백엔드로 둡니다. | DB는 PostgreSQL, 인증은 Supabase로 확정하며 Supabase는 내부 인프라로만 사용합니다. |
| RLS 중심으로 권한을 설명합니다. | Core에서 공통 권한을 검사하고 DB 정책은 보조로 검토합니다. |
| 기기 캘린더 접근을 연동의 중심으로 둡니다. | 기존 일정 표시는 expo-calendar, 자체 캘린더 제공은 CalDAV가 담당합니다. |
| 자체 일정의 외부 반영 경로가 없습니다. | CalDAV가 같은 Core 일정에 대한 표준 접근 경로를 제공합니다. |
| Edge Functions 예약 실행을 우선합니다. | 상시 구동 단일 서버의 내장 스케줄러가 DB 예약 상태를 기준으로 실행합니다. |
| 자체 백엔드 서버를 제외합니다. | 단일 자체 서버를 기본 구조에 포함합니다. |

## 연동 범위와 호환성

expo-calendar는 휴대폰에 이미 있는 일정을 앱에서 보는 경로이고 CalDAV는 자체 캘린더를 외부 클라이언트에 제공하는 경로입니다. 두 역할을 합쳐 하나의 공급자 서버 동기화 기능으로 설명하지 않습니다.

- 기기 기존 일정은 expo-calendar로 읽고 원본은 해당 캘린더에 유지합니다.
- 자체 일정은 REST와 CalDAV에서 같은 Core 데이터를 사용합니다.
- CalDAV 외부 쓰기를 제공하면 같은 권한·검증·알림 경로를 거칩니다.
- CalDAV 제공만으로 모든 Apple·Google·Samsung 앱의 연결을 보장하지 않습니다.
- 공급자 계정 서버 직접 복제는 별도 기능으로 초기 범위에서 제외합니다.

CalDAV는 iCalendar 기반 캘린더 접근 표준입니다. 클라이언트의 계정 추가·인증·읽기·쓰기와 동기화 주기는 실기기 검증이 필요합니다. 각 앱의 직접 연결 가능 여부와 추가 동기화 구성 필요성은 현재 확실하지 않습니다. [RFC 4791](https://www.rfc-editor.org/rfc/rfc4791)

Android Calendar Provider 접근과 계정 서버 동기화도 구분해야 합니다. 기기에 노출되는 기존 일정 범위와 삼성 계정별 실제 동작은 확인이 필요합니다. [Android 공식 문서](https://developer.android.com/identity/providers/calendar-provider)

## CalDAV 구현 검토

표준 인터페이스 선언과 클라이언트 호환성 확보는 다른 단계입니다. 다음은 구현·검증 항목이며 완료 사항이 아닙니다.

- 계정·컬렉션 탐색과 구성원별 접근 가능한 캘린더 노출을 확인해야 합니다.
- UID와 리소스 경로를 안정적으로 유지해야 합니다.
- 조회·생성·수정·삭제와 조건부 요청을 지원 범위에 맞게 처리해야 합니다.
- 반복 원본·회차 예외·종일·시간대의 왕복 변환을 확인해야 합니다.
- 지원하지 않는 속성을 보존하거나 명시적으로 거절하는 정책을 정해야 합니다.
- 삭제·재접속 처리와 증분 동기화 채택 여부를 정해야 합니다.

ETag와 Core 버전은 REST·CalDAV 동시 수정에서도 일관되어야 합니다. 동기화 확장과 토큰 복구 정책은 별도 확정합니다. [RFC 4791](https://www.rfc-editor.org/rfc/rfc4791), [RFC 6578](https://www.rfc-editor.org/rfc/rfc6578)

그룹·초대 관리는 앱의 REST 사용 흐름을 중심으로 정합니다. 외부 클라이언트에는 지원하는 일정 접근 기능을 제공하며, 참석 투표 같은 제외 기능을 추가하지 않습니다.

## 반복 일정과 동시 수정

반복 규칙·종료 조건·회차 예외와 시간대는 Core의 공통 모델에서 다룹니다. 프로토콜별 반복 엔진을 따로 만들면 같은 일정의 날짜나 수정 범위가 달라질 수 있습니다.

- 종일 일정은 날짜 범위로 관리하고 종료일 포함 여부를 정의합니다.
- 시간 지정 반복 일정은 기준 시간대를 보존합니다.
- 특정 회차의 수정·취소를 원본과 구분합니다.
- 앱의 초기 수정 범위는 ‘이번 일정만’과 ‘전체 일정’을 권장합니다.
- ‘이후 모든 일정’과 외부 클라이언트의 추가 변경 형태는 처리 범위를 정해야 합니다.
- 낙관적 버전 검사로 오래된 변경을 감지하는 방식을 권장합니다.

CalDAV 변환에는 UID, 반복 규칙과 예외 회차의 의미 보존이 필요합니다. 지원하지 않는 반복 데이터를 조용히 단순화해 저장하지 않도록 정책을 정합니다. [iCalendar RFC 5545](https://www.rfc-editor.org/rfc/rfc5545)

## 권한·인증·초대

모든 Adapter는 검증된 내부 구성원 식별자와 접근 범위를 Core에 전달하고 Core는 현재 멤버십을 검사해야 합니다. DB 직접 변경으로 우회하는 경로를 두지 않습니다.

- 구성원은 그룹 일정 조회·등록·수정·삭제가 가능하도록 하는 정책을 권장합니다.
- 그룹 관리와 구성원 제거는 소유자에게 제한하는 정책을 권장합니다.
- 탈퇴·제거 이후 REST·CalDAV 접근을 같은 기준으로 차단해야 합니다.
- 초대는 서버에서 검증하고 만료·취소·중복 수락을 처리해야 합니다.
- 개인 일정은 초대할 수 없는 개인 전용 그룹으로 처리하는 방식을 권장합니다.

권한 세부안과 소유자 탈퇴 방식은 미결정입니다. 외부 클라이언트에 이미 내려간 데이터의 삭제까지 서버가 보장한다고 표현하지 않습니다.

Apple·Google 로그인과 CalDAV 접속 인증에 같은 화면이나 자격 증명을 사용할 수 있다고 가정하지 않습니다. 인증 방식은 클라이언트 호환성과 발급·철회·기기 교체 흐름을 검토한 뒤 정합니다. MCP의 인증·접근 범위는 도입 시 검토합니다.

## 알림과 변경 반영

가족이 일정을 추가하면 다른 구성원이 앱을 열지 않아도 알림 대상과 시점이 계산되어야 합니다. 화면 변경 반영과 일정 시각 알림은 별개이며 REST 재조회나 지속 연결로 알림 예약을 대신하지 않습니다.

단일 서버 예약 작업이 저장된 상태를 기준으로 발송하는 방식을 권장합니다. REST·CalDAV 변경 모두 같은 Core 경로로 예약 상태에 반영해야 합니다.

- 개인 수신 설정, 기기 토큰과 다음 반복 알림을 관리해야 합니다.
- 변경·삭제·탈퇴에 따라 예약과 수신자를 갱신해야 합니다.
- 재시작 후 복구와 중복 실행 처리를 설계해야 합니다.
- CalDAV 클라이언트 자체 알림과 앱 푸시의 중복 정책을 정해야 합니다.

expo-notifications는 모바일 알림에 활용하며 서버 예약을 대신하지 않습니다. 푸시의 정확한 도착 시각을 보장한다고 표현하지 않습니다. [Expo 알림 문서](https://docs.expo.dev/versions/latest/sdk/notifications/)

## UX와 중복 표시

Core·Adapter는 내부 설계 용어입니다. 그룹 참여와 일정 작성은 외부 캘린더 설정 없이 완료할 수 있어야 합니다.

- 초대받은 그룹 이름과 참여 버튼을 표시하고 로그인 후 초대 맥락을 유지합니다.
- 일정 작성 시 공유 대상 그룹을 글자로 보여줍니다.
- 이름과 색상을 함께 표시하고 글씨 확대에도 주요 동작을 유지합니다.
- 기기 권한은 ‘휴대폰 일정 함께 보기’를 선택할 때 요청합니다.
- 자체 캘린더의 외부 연결은 선택 설정으로 분리합니다.
- 개인별 표시·숨김은 다른 구성원에게 영향을 주지 않도록 합니다.

CalDAV로 기기에 연결한 자체 일정이 REST와 expo-calendar 양쪽에서 보이면 중복됩니다. 해당 기기 캘린더를 통합 표시에서 제외하는 방식을 먼저 검증해야 합니다. 이름이나 제목·시간만으로 서로 다른 일정을 병합하지 않습니다.

외부 기존 일정의 그룹 복사는 초기 제외 권장안을 유지합니다. 향후 도입하면 원본 변경이 자동 반영되지 않음을 설명하고 ‘그룹에 복사’라고 표현합니다. CalDAV로 제공한 자체 일정은 이러한 복사본이 아닙니다.

## 권장 구현·검증 순서

Core와 REST를 먼저 구현하고 CalDAV를 같은 규칙에 연결하는 순서를 따릅니다. Core 데이터 모델은 초기부터 CalDAV 호환(UID·ETag·리소스 경로, iCalendar 호환 반복·예외, REST·CalDAV 공용 버전 체계)으로 설계하되, CalDAV Adapter 구현은 REST 완성 이후로 둡니다. CalDAV 최초 공개는 읽기 전용으로 확정하며 쓰기는 왕복 검증 후 확장합니다.

1. 서버·DB·인증과 공통 권한·반복·버전 모델을 정합니다.
2. Core와 REST로 그룹·초대·개인 설정·일정 기능을 구현합니다.
3. 알림 예약과 변경 후 재조회 흐름을 구현합니다.
4. expo-calendar 기존 일정 표시와 권한 흐름을 확인합니다.
5. CalDAV 조회·변환을 검증하고 쓰기 제공 시 왕복 변경·충돌을 검증합니다.
6. 기기별 연결·중복 표시·알림·탈퇴 후 접근을 확인하고 지원 범위를 명시합니다.

MCP는 초기 완료 조건에 포함하지 않습니다. 실제 필요가 확인되면 같은 Core에 연결합니다. 이번 작업은 문서 갱신이며 빌드·서버 실행·실기기 테스트는 수행하지 않았습니다.

## 확정 사항과 미결정 사항

이번 검토에서 다음 항목을 확정했습니다.

- 서버 프레임워크는 Fastify, DB는 PostgreSQL, 인증은 Supabase(내부 인프라)로 확정합니다.
- 알림은 상시 구동 단일 서버의 내장 스케줄러가 DB 예약 상태를 기준으로 발송하고 푸시는 Expo Push를 사용합니다.
- CalDAV 최초 공개는 읽기 전용으로 확정하며 쓰기는 왕복 검증 후 확장합니다.
- Core 데이터 모델은 초기부터 CalDAV 호환으로 설계하되 CalDAV Adapter 구현은 REST 완성 이후로 둡니다.
- MCP는 후순위 선택 기능으로 두고 초기 범위에서 제외합니다.

다음 세부 항목은 후속 결정이 필요합니다.

- 배포·호스팅 환경과 예약 작업 재시도·복구 정책을 정해야 합니다.
- CalDAV 쓰기 확장 시 대상 클라이언트·접속 인증 방식을 정해야 합니다.
- 반복·예외 지원 범위, iCalendar 속성 보존과 충돌 응답을 정해야 합니다.
- 그룹 권한·초대 만료·소유자 탈퇴와 개인별 알림 정책을 정해야 합니다.
- 앱 변경 반영 방식(재조회·지속 연결)을 정해야 합니다.
- 기기 중복 표시와 알림 중복 처리 방식을 검증해야 합니다.

이번 갱신에서는 CalDAV·iCalendar·WebDAV 동기화 RFC를 대조했습니다. 공식 문서는 표준의 근거이며 moa-square 호환성 인증을 의미하지 않습니다.

- [RFC 4791](https://www.rfc-editor.org/rfc/rfc4791)에서 CalDAV 접근 구조를 확인했습니다.
- [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545)에서 iCalendar 표현 기준을 확인했습니다.
- [RFC 6578](https://www.rfc-editor.org/rfc/rfc6578)에서 선택적으로 검토할 증분 동기화 구조를 확인했습니다.
- [Expo Calendar](https://docs.expo.dev/versions/latest/sdk/calendar/)와 [Android Calendar Provider](https://developer.android.com/identity/providers/calendar-provider)는 기존 기기 일정 접근 검토의 근거로 유지합니다.
- [Expo 알림](https://docs.expo.dev/versions/latest/sdk/notifications/)은 모바일 알림 검토의 근거로 유지합니다.

실제 구현 시 선택한 SDK와 대상 클라이언트의 공식 문서를 다시 확인해야 합니다. MCP 세부 프로토콜은 이번 범위에서 설계·검증하지 않았습니다.
