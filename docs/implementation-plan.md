# moa-square 구현 계획

이 문서는 moa-square를 단계별로 구현하기 위한 실행 계획입니다. 각 단계는 AI 에이전트가 순서대로 읽고 구현할 수 있도록 목표, 선행 조건, 구현 대상, 완료 기준, 참조 문서를 함께 제시합니다. 제품 방향은 [제품 요구사항](./product-requirements.md), 구조는 [아키텍처 설계](./proposed-architecture.md), 판단 근거와 미결정 항목은 [적합성 검토](./design-review.md)를 따릅니다.

## 확정된 기술 스택

이번 계획은 다음 확정 사항을 전제로 합니다. 미확정 세부 항목은 각 단계의 미결정 표시를 따릅니다.

- 서버 프레임워크는 Fastify이며 Calendar Core는 프레임워크에 독립된 순수 TypeScript 모듈로 둡니다.
- DB는 PostgreSQL, 인증은 Supabase(내부 인프라)이며 앱은 REST로만 접근합니다.
- 알림은 상시 구동 단일 서버의 내장 스케줄러가 DB 예약 상태를 기준으로 발송하고 푸시는 Expo Push를 사용합니다.
- 모바일은 React Native + Expo + TypeScript, 라우팅은 Expo Router, 조회·캐시는 TanStack Query를 사용합니다.
- CalDAV 최초 공개는 읽기 전용이며 쓰기는 왕복 검증 후 확장합니다. Core 데이터 모델은 초기부터 CalDAV 호환으로 설계합니다.
- MCP는 후순위 선택 기능이며 초기 구현 범위에서 제외합니다.

## 구현 원칙

Calendar Core에 권한·일정 규칙·반복·버전 충돌 처리를 모으고 Adapter는 프로토콜 입출력 변환만 담당합니다. Adapter가 DB를 직접 변경하거나 권한 규칙을 복제하지 않습니다. 모든 자체 공유 일정의 조회·변경은 Core를 거칩니다.

해결책은 심플하게 유지하고 핵심만 최소한으로 구현합니다. 동작에 불필요한 코드, 예외 처리, 부가 기능을 덧붙이지 않습니다. 각 단계는 이전 단계의 완료 기준을 충족한 뒤 시작합니다.

## 테스트 전략

테스트는 전 단계에 일괄 적용하지 않고 계층 성격에 맞춰 차등 적용합니다. 테스트로 명세를 먼저 고정하는 이득이 큰 계층과 실기기·수동 검증이 더 적합한 계층이 나뉘기 때문입니다.

- 단계 1~2의 Calendar Core와 권한·버전·반복 로직은 순수 함수로 검증할 수 있고 회귀 위험이 크므로 TDD로 구현합니다. 실패하는 테스트를 먼저 작성하고 이를 통과시키는 코드를 구현합니다.
- 단계 3~4의 REST와 알림 예약은 통합 테스트를 구현과 나란히 작성합니다. 테스트 우선을 강제하지 않되 완료 기준의 통합 테스트를 함께 둡니다.
- 단계 5~8의 모바일 UI, expo-calendar, CalDAV 클라이언트 호환은 단위 테스트로 선행 명세하기 어렵고 실기기 동작을 봐야 하므로 실기기·수동 검증을 중심에 둡니다. 안정된 순수 로직에 한해 선택적으로 단위 테스트를 붙입니다.

단계 0의 스모크 테스트는 기능 검증이 아니라 테스트 러너와 프리셋이 동작함을 실증하는 최소 검증입니다.

## 단계 개요

| 단계 | 목표                         | 핵심 산출물                                  |
| ---- | ---------------------------- | -------------------------------------------- |
| 0    | 저장소·개발 환경 구성        | 모노레포 구조, 툴체인, 린트·테스트 설정      |
| 1    | 데이터 모델과 권한·버전 기반 | PostgreSQL 스키마, 인증 연동, 권한·버전 규칙 |
| 2    | Calendar Core 도메인 로직    | 그룹·멤버십·초대·일정·반복·개인 설정 로직    |
| 3    | REST Adapter                 | 그룹·초대·일정·개인 설정 REST API            |
| 4    | 알림 예약과 스케줄러         | 예약 상태 관리, 상시 스케줄러, Expo Push     |
| 5    | 모바일 앱                    | 가입·초대·일정 CRUD·표시숨김·알림 수신       |
| 6    | expo-calendar 통합 표시      | 기기 기존 일정 읽기·통합 표시·중복 제외      |
| 7    | CalDAV Adapter (읽기 전용)   | 컬렉션 탐색·조회·iCalendar 변환              |
| 8    | CalDAV 쓰기 확장 (조건부)    | 외부 수정 왕복·충돌·알림 갱신                |

MCP Adapter는 실제 필요가 확인될 때 같은 Core에 연결하며 이 계획에는 포함하지 않습니다.

## 단계 0: 저장소와 개발 환경 구성

### 목표

이후 모든 단계가 공유하는 모노레포 구조와 개발 도구를 구성합니다.

### 구현 대상

- [아키텍처 설계 - 코드 구성](./proposed-architecture.md#코드-구성과-개발-도구)의 폴더 구조에 따라 `mobile/`과 `server/`를 생성합니다.
- 패키지 매니저는 pnpm, 런타임은 Node.js LTS를 사용합니다.
- 서버는 Fastify와 TypeScript, 모바일은 Expo와 TypeScript로 초기화합니다.
- 공통 린트(ESLint)·포매터(Prettier)·타입 검사(tsc) 설정을 둡니다.
- 테스트 러너는 서버 Vitest, 모바일 Jest(jest-expo 프리셋)로 지정합니다.
- React Native Testing Library는 모바일 테스트 유틸리티로 사용하며 테스트 러너로 두지 않습니다.

### 완료 기준

- `server/`와 `mobile/`이 각각 타입 검사에 성공합니다.
- 각 워크스페이스의 스모크 테스트 한 개가 통과해 테스트 러너와 프리셋 동작을 실증합니다.
- 서버가 기동해 헬스 체크 엔드포인트에 응답합니다.

### 참조

## 단계 1: 데이터 모델과 권한·버전 기반

### 목표

CalDAV 호환을 전제로 한 데이터 모델과 인증·권한·버전 규칙의 기반을 만듭니다. 이 단계의 모델 설계가 이후 재설계를 좌우하므로 CalDAV 요구를 초기부터 반영합니다.

### 선행 조건

단계 0 완료.

### 구현 대상

- [아키텍처 설계 - 저장소와 논리 모델](./proposed-architecture.md#저장소와-논리-모델)의 논리 요구사항을 PostgreSQL 스키마로 구체화합니다. 대상 항목은 구성원·그룹·멤버십, 초대, 일정, 반복·예외, 개인 설정, 알림, CalDAV 리소스입니다.
- 일정 모델에 CalDAV 호환 필드를 포함합니다. 안정적 UID, 리소스 경로, ETag에 대응하는 버전, 기준 시간대를 저장합니다.
- 반복 규칙과 회차 예외를 iCalendar(RFC 5545) 의미가 보존되도록 표현합니다. 종일 일정은 날짜 범위로, 시간 지정 일정은 기준 시간대를 보존해 저장합니다.
- Supabase 인증으로 검증한 자격 증명을 내부 구성원 식별자로 연결하는 인증 계층을 만듭니다.
- Core가 식별자와 접근 범위를 받아 현재 멤버십을 검사하는 권한 검사 기반을 만듭니다. RLS는 보조 방어로만 검토하고 Core 검사를 대체하지 않습니다.
- 낙관적 버전 검사로 오래된 변경을 감지하는 규칙을 정의합니다.
- 권한 검사와 버전 검사 규칙은 TDD로 구현합니다. 실패하는 테스트를 먼저 작성하고 이를 통과시키는 코드를 구현합니다.

### 완료 기준

- 스키마 마이그레이션이 적용되고 각 테이블의 관계 제약이 검증됩니다.
- 인증 계층이 자격 증명을 내부 식별자로 연결하는 단위 테스트를 통과합니다.
- 권한 검사와 버전 검사의 단위 테스트를 통과합니다.
- 개인 일정을 초대 불가한 개인 전용 그룹으로 표현할 수 있습니다.

### 미결정

- iCalendar 미지원 속성의 보존·거절 정책은 단계 7 이전에 확정합니다.
- 소유자 탈퇴 처리 방식은 단계 2 권한 로직 확정 시 함께 정합니다.

## 단계 2: Calendar Core 도메인 로직

### 목표

전송 프로토콜과 독립된 공통 일정 로직을 구현합니다. Core는 순수 TypeScript 모듈로 두어 REST·CalDAV가 공유합니다. 이 단계의 도메인 규칙은 TDD로 구현하며 실패하는 테스트를 먼저 작성합니다.

### 선행 조건

단계 1 완료.

### 구현 대상

[아키텍처 설계 - Calendar Core](./proposed-architecture.md#calendar-core)의 규칙을 구현합니다.

- 그룹·멤버십·개인 전용 그룹·초대 수락과 권한을 관리합니다. 구성원은 그룹 일정 조회·등록·수정·삭제가 가능하고, 그룹 관리와 구성원 제거는 소유자로 제한합니다.
- 초대를 서버에서 검증하고 만료·취소·중복 수락을 처리합니다.
- 일정 CRUD와 날짜·시간·종일 일정의 유효성을 검사합니다.
- 반복 규칙·회차 예외·시간대와 기간별 조회를 처리합니다. 수정 범위는 '이번 일정만'과 '전체 일정'을 우선 지원합니다.
- 개인별 그룹 표시·숨김과 개인별 알림 설정을 관리합니다. 개인 설정은 다른 구성원에게 영향을 주지 않습니다.
- 일정 버전과 동시 수정 충돌을 낙관적 버전 검사로 처리합니다.
- 변경에 따른 알림 예약 갱신에 필요한 상태를 저장합니다.

### 완료 기준

- 그룹·초대·일정·반복·개인 설정 로직이 단위 테스트를 통과합니다.
- 탈퇴·제거 이후 접근이 차단되는지 테스트로 검증합니다.
- 동시 수정 시 오래된 버전 변경이 거부되는지 테스트로 검증합니다.

### 미결정

- '이후 모든 일정' 수정 범위와 소유자 탈퇴 처리 방식은 이 단계에서 확정합니다.

## 단계 3: REST Adapter

### 목표

모바일 앱의 기본 서버 인터페이스를 구현합니다. 그룹·초대·일정·개인 설정 요청을 Core 호출로 변환합니다.

### 선행 조건

단계 2 완료.

### 구현 대상

[아키텍처 설계 - REST Adapter](./proposed-architecture.md#rest-adapter)를 구현합니다.

- 그룹·초대·일정·개인 설정에 대한 REST 엔드포인트를 Fastify로 구현하고 결과를 JSON과 HTTP 응답으로 반환합니다.
- 버전 등 충돌 감지에 필요한 정보를 요청·응답에 포함합니다.
- 인증 계층이 검증한 내부 식별자와 접근 범위를 Core에 전달합니다. Adapter는 DB를 직접 변경하지 않습니다.
- 초기 변경 반영은 화면 복귀·변경 후 재조회를 전제로 설계합니다.

### 완료 기준

- 그룹 생성·초대·일정 CRUD·개인 설정 변경이 REST로 동작하는 통합 테스트를 통과합니다.
- 오래된 버전으로의 수정 요청이 충돌로 거부됩니다.
- 권한 없는 요청이 Core 검사에서 차단됩니다.

### 미결정

- 지속 연결의 필요성과 방식, 정확한 API 명세 세부는 이 단계에서 구체화합니다.

### 참조

- [아키텍처 설계 - REST Adapter](./proposed-architecture.md#rest-adapter)

## 단계 4: 알림 예약과 스케줄러

### 목표

앱 실행과 무관하게 서버가 알림 발송 시점을 관리하는 예약 체계를 구현합니다.

### 선행 조건

단계 3 완료.

### 구현 대상

[아키텍처 설계 - 알림과 운영](./proposed-architecture.md#알림과-운영)을 구현합니다.

- 개인 수신 설정, 기기 토큰, 다음 반복 알림을 관리합니다.
- 상시 구동 서버의 내장 스케줄러가 DB 예약 상태를 기준으로 발송합니다.
- REST 변경이 같은 Core 경로로 예약 상태에 반영되도록 합니다. 수정·삭제·탈퇴에 따라 발송 대상과 시점을 갱신합니다.
- 재시작 후 복구와 중복 발송 방지를 위한 상태를 관리합니다.
- 푸시 발송은 Expo Push로 구현합니다.

### 완료 기준

- 일정 생성·수정·삭제가 예약 상태에 반영되는 테스트를 통과합니다.
- 서버 재시작 후 누락·중복 없이 예약이 복구되는지 검증합니다.

### 미결정

- 재시도 정책과 CalDAV 클라이언트 자체 알림과의 중복 처리 정책은 단계 8에서 확정합니다.

## 단계 5: 모바일 앱

### 목표

디지털 취약계층 친화 UX로 가입·초대부터 일정 관리까지 완결하는 앱을 구현합니다. 외부 캘린더 설정 없이 그룹 참여와 일정 작성을 완료할 수 있어야 합니다.

### 선행 조건

단계 3 완료. 화면과 일정 기능 구현은 단계 4와 병행할 수 있으나 알림 수신 동작 확인은 단계 4 완료 이후에 수행합니다.

### 구현 대상

[적합성 검토 - UX와 중복 표시](./design-review.md#ux와-중복-표시)와 제품 요구사항을 따릅니다.

- Expo Router로 화면을 구성하고 TanStack Query로 REST 조회·캐시를 관리합니다. 화면 상태는 useState·useReducer, 간단한 전역 설정은 Context를 사용합니다.
- 초대받은 그룹 이름과 참여 버튼을 표시하고 로그인 후 초대 맥락을 유지합니다.
- 일정 생성·수정·삭제, 날짜·시간·종일·반복·알림·메모·라벨을 지원합니다.
- 일정 작성 시 공유 대상 그룹을 글자로 보여주고, 그룹은 이름과 색상을 함께 표시합니다.
- 그룹별 일정 표시·숨김을 개인별로 선택합니다.
- 글씨 확대에도 주요 동작을 유지하고 색상만으로 정보를 구분하지 않습니다.
- expo-notifications로 알림을 수신합니다.

### 완료 기준

검증은 실기기·수동 확인을 중심에 둡니다. UI는 단위 테스트로 선행 명세하지 않고, 안정된 순수 로직에 한해 선택적으로 단위 테스트를 붙입니다.

- 가입·초대 수락·일정 CRUD·표시숨김이 실제 기기에서 동작합니다.
- 큰 글씨 설정과 색상 비의존 표시가 확인됩니다.

### 참조

## 단계 6: expo-calendar 통합 표시

### 목표

기기에 등록된 기존 일정을 읽어 앱 화면에 함께 표시합니다. 기존 일정 직접 수정과 자동 그룹 복사는 제외합니다.

### 선행 조건

단계 5 완료. 기기 기존 일정의 통합 표시는 이 시점에 구현하고, CalDAV로 연결된 자체 일정의 중복 제외는 단계 7 완료 이후에 검증합니다.

### 구현 대상

[아키텍처 설계 - expo-calendar와 데이터 원본](./proposed-architecture.md#expo-calendar와-데이터-원본)을 따릅니다.

- '휴대폰 일정 함께 보기'를 선택할 때 기기 권한을 요청합니다.
- expo-calendar로 기기 기존 일정을 읽어 통합 표시합니다. 원본은 해당 외부 캘린더에 유지합니다.
- CalDAV로 기기에 연결된 자체 일정이 expo-calendar에도 나타나 REST 일정과 중복되는 경우, 해당 기기 캘린더를 통합 표시에서 제외합니다. 이름·제목·시간만으로 병합하지 않습니다.

### 완료 기준

- 권한 흐름과 기존 일정 통합 표시가 실제 기기에서 동작합니다.
- 기기별 통합 표시 제외 선택이 저장·복원됩니다.

### 미결정

- 중복 식별과 기기별 선택 저장 방식은 실기기로 검증해 확정합니다.

### 참조

- [아키텍처 설계 - expo-calendar와 데이터 원본](./proposed-architecture.md#expo-calendar와-데이터-원본)
- [Expo Calendar 문서](https://docs.expo.dev/versions/latest/sdk/calendar/)

## 단계 7: CalDAV Adapter (읽기 전용)

### 목표

자체 공유 캘린더를 외부 클라이언트에 읽기 전용으로 제공합니다. 같은 Core 일정을 iCalendar로 변환합니다.

### 선행 조건

단계 3 완료. Core 데이터 모델이 단계 1에서 CalDAV 호환으로 설계되어 있어야 합니다.

### 구현 대상

[아키텍처 설계 - CalDAV Adapter](./proposed-architecture.md#caldav-adapter)와 RFC 4791·5545를 따릅니다.

- 접근 가능한 그룹을 캘린더 컬렉션으로 제공합니다.
- 컬렉션 탐색과 기간 조회 요청을 Core 호출로 변환합니다.
- Core 일정을 iCalendar로 변환합니다. 반복 원본·회차 예외·종일·시간대의 의미를 보존합니다.
- 리소스 URL·UID·ETag를 Core 식별자·버전과 일관되게 연결합니다.
- 인증 계층이 검증한 구성원 식별자로 접근을 제한하며 탈퇴·제거 시 REST와 같은 기준으로 차단합니다.
- 지원하지 않는 iCalendar 속성의 보존·거절 정책을 적용합니다.

### 완료 기준

iCalendar 변환 같은 순수 로직은 단위 테스트로 검증하고, 클라이언트 호환은 실기기 검증을 중심에 둡니다.

- 외부 클라이언트가 컬렉션을 탐색하고 기간 일정을 조회할 수 있습니다.
- 반복·예외·종일·시간대가 iCalendar 변환에서 의미를 유지하는 단위 테스트를 통과합니다.
- 대상 클라이언트별 연결·조회 동작을 실기기로 검증하고 지원 범위를 명시합니다.

### 미결정

- 증분 동기화(WebDAV sync-token, RFC 6578) 채택 여부와 대상 클라이언트·접속 인증 방식을 이 단계에서 확정합니다.

### 참조

- [아키텍처 설계 - CalDAV Adapter](./proposed-architecture.md#caldav-adapter)
- [적합성 검토 - CalDAV 구현 검토](./design-review.md#caldav-구현-검토)
- [RFC 4791](https://www.rfc-editor.org/rfc/rfc4791), [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545), [RFC 6578](https://www.rfc-editor.org/rfc/rfc6578)

## 단계 8: CalDAV 쓰기 확장 (조건부)

### 목표

외부 클라이언트의 허용된 일정 변경을 같은 Core 일정에 반영합니다. 이 단계는 단계 7의 읽기 전용 검증이 끝난 뒤 왕복 변환·충돌 검증을 마치고 진행합니다.

### 선행 조건

단계 4와 단계 7 완료. 단계 7은 단계 4 완료를 보장하지 않으므로 예약 갱신 경로를 연결하려면 단계 4가 함께 완료되어야 합니다.

### 구현 대상

- 외부 생성·수정·삭제와 조건부 요청을 Core 호출로 변환하고 공통 권한·충돌·알림 갱신 규칙을 적용합니다.
- ETag와 Core 버전이 REST·CalDAV 동시 수정에서도 일관되게 유지되도록 합니다.
- 삭제·재접속 처리를 설계합니다.
- CalDAV 변경도 단계 4의 예약 갱신 경로를 거치도록 연결합니다.

### 완료 기준

충돌 감지와 왕복 변환은 단위·통합 테스트로 검증하고, 클라이언트 쓰기 호환은 실기기 검증을 중심에 둡니다.

- 외부 수정이 같은 Core 일정에 반영되고 REST 조회로 확인됩니다.
- REST·CalDAV 동시 수정에서 충돌이 일관되게 감지되는 테스트를 통과합니다.
- 반복·예외의 왕복 변경이 의미를 유지합니다.

### 미결정

- CalDAV 클라이언트 자체 알림과 앱 푸시의 중복 정책을 이 단계에서 확정합니다.
