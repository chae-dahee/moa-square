# moa-square 구현 계획

이 문서는 Google Calendar 전용 MVP를 단계별로 구현하기 위한 계획입니다. 제품 범위는 [제품 요구사항](./product-requirements.md), 구조는 [아키텍처 설계](./proposed-architecture.md), 판단 근거는 [적합성 검토](./design-review.md)를 따릅니다.

## 확정된 기술 방향

- 모바일은 React Native + Expo + TypeScript를 사용합니다.
- 라우팅은 Expo Router, 원격 조회와 캐시는 TanStack Query를 사용합니다.
- Google OAuth로 인증하고 Google Calendar API를 호출합니다.
- 공유 그룹은 Google 보조 캘린더, 구성원 권한은 ACL로 표현합니다.
- 일정과 공유 권한은 Google Calendar를 원본으로 사용합니다.
- 변경 반영은 재조회와 sync token 기반 증분 동기화로 시작합니다.

## 구현 원칙

Google API 응답 변환과 화면 로직을 분리합니다. 두 번째 공급자를 추가하기 전에는 공급자 추상화나 자체 일정 모델을 과도하게 만들지 않습니다.

순수한 응답 변환과 권한 판단은 단위 테스트를 먼저 작성할 수 있습니다. OAuth, 실제 Calendar API, 초대와 기기 동작은 테스트 계정과 실제 기기 검증을 중심으로 확인합니다. 외부 API 테스트는 운영 계정이나 개인 캘린더를 사용하지 않습니다.

## 단계 1: Google OAuth·Calendar API 검증

### 목표

실제 iOS와 Android 환경에서 Google 계정 연결과 Calendar API 접근 가능성을 먼저 검증합니다.

### 구현 대상

- Google Cloud 프로젝트와 OAuth 동의 화면을 구성합니다.
- iOS와 Android OAuth 클라이언트 및 리디렉션을 구성합니다.
- 최소 Calendar 권한 범위를 확정합니다.
- 로그인·로그아웃과 토큰 보안 저장을 구현합니다.
- 사용자가 접근할 수 있는 Calendar 목록을 조회합니다.

### 완료 기준

- iOS와 Android에서 Google 로그인과 권한 동의가 동작합니다.
- 로그인한 사용자의 Calendar 목록을 조회할 수 있습니다.
- 인증 만료와 연결 해제 흐름을 확인합니다.

### 검증 방식

- 인증 상태 변환과 오류 매핑은 단위 테스트로 검증합니다.
- OAuth와 API 호출은 별도 테스트 계정과 실제 기기로 검증합니다.

---

## 단계 2: 공유 그룹

### 목표

Google 보조 캘린더와 ACL로 공유 그룹 생성·초대·권한 관리를 구현합니다.

### 선행 조건

단계 1 완료.

### 구현 대상

- 그룹 생성 시 보조 캘린더를 생성합니다.
- Google 계정 이메일로 `reader` 또는 `writer` 권한을 부여합니다.
- 초대받은 사용자가 캘린더를 자신의 Calendar 목록에 추가하도록 안내합니다.
- 그룹 이름과 색상을 표시하고 표시·숨김 선택을 기기에 저장합니다.
- 권한 변경과 구성원 제거를 구현합니다.

### 완료 기준

- 두 개의 테스트 계정으로 그룹 생성·초대·참여가 동작합니다.
- 참여자가 권한 범위에 따라 일정을 조회하거나 변경할 수 있습니다.
- 구성원 제거 후 접근이 차단됩니다.

### 구현 중 결정

- 초대 링크와 Calendar 목록 추가 UX를 확정합니다.
- 생성자 탈퇴와 소유권 처리 범위를 확정합니다.

---

## 단계 3: 일정 기능

### 목표

Google Calendar Event를 이용해 기본 일정 기능을 구현합니다.

### 선행 조건

단계 2 완료.

### 구현 대상

- 일정 생성·조회·수정·삭제를 구현합니다.
- 날짜·시간, 종일, 시간대, 메모와 알림을 지원합니다.
- 반복 일정과 특정 회차 예외를 처리합니다.
- API 오류와 권한 부족을 사용자에게 명확히 표시합니다.

### 완료 기준

- 일정 CRUD가 moa-square와 Google Calendar 양쪽에서 확인됩니다.
- 종일 일정과 시간 지정 일정이 시간대 변경 후에도 올바르게 표시됩니다.
- 반복 일정 전체와 특정 회차 수정·삭제가 동작합니다.

### 구현 중 결정

- ‘이후 모든 일정’ 수정 지원 여부를 확정합니다.

## 단계 4: 동기화

### 목표

Google Calendar에서 발생한 변경을 앱에 안정적으로 반영합니다.

### 선행 조건

단계 3 완료.

### 구현 대상

- 앱 실행, 화면 복귀와 수동 새로고침 시 데이터를 다시 조회합니다.
- 변경 작업 성공 후 관련 TanStack Query 캐시를 무효화합니다.
- 초기 전체 조회에서 sync token을 받고 이후 변경분만 조회합니다.
- sync token 만료 시 전체 조회로 복구합니다.

### 완료 기준

- Google Calendar에서 생성·수정·삭제한 일정이 앱 재조회 후 반영됩니다.
- 앱에서 변경한 일정이 Google Calendar에 반영됩니다.
- sync token 만료 상황에서 데이터 누락 없이 복구됩니다.

## 단계 5: 모바일 UX 완성

### 목표

가입부터 공유 일정 관리까지 학습 부담이 낮은 흐름을 완성합니다.

### 선행 조건

단계 4 완료.

### 구현 대상

- 로그인, 그룹 생성·초대·참여와 일정 관리 화면을 연결합니다.
- 일정 작성 시 공유 대상 캘린더를 이름으로 명확히 표시합니다.
- 그룹 이름과 색상을 함께 표시합니다.
- 글씨 확대에도 주요 동작을 유지합니다.
- 로딩·빈 화면·권한 부족·네트워크 오류 상태를 처리합니다.

### 완료 기준

- 처음 사용하는 사람이 안내 없이 그룹 생성·초대·일정 등록을 완료할 수 있습니다.
- 큰 글씨와 색상 비의존 표시를 실제 기기에서 확인합니다.

## 단계 6: 출시 전 검증

### 목표

지원 환경과 배포 요건을 확인하고 MVP 출시 범위를 확정합니다.

### 선행 조건

단계 5 완료.

### 구현 대상

- iPhone과 Android 실제 기기에서 핵심 흐름을 검증합니다.
- 개인 Google 계정 간 공유와 가능한 경우 Workspace 계정 제약을 확인합니다.
- API 제한, 네트워크 단절, 인증 만료와 권한 철회를 확인합니다.
- Google OAuth 앱 검증과 개인정보처리방침 요건을 충족합니다.

### 완료 기준

- 지원 계정과 기기 범위를 문서화합니다.
- 핵심 흐름의 차단 오류가 없습니다.
- 공개 배포에 필요한 OAuth 설정과 정책 문서가 준비되어 있습니다.

## 후속 확장 판단

MVP 사용 데이터를 확인한 뒤 백그라운드 변경 알림 서버, 앱 고유 저장소와 다른 캘린더 공급자 지원의 필요성을 각각 판단합니다. 필요가 확인되지 않은 기능은 미리 구현하지 않습니다.
